# 밸류에이션 방법론 스펙

DART(공시) 재무 + KRX(공식 시세)로 상대가치 배수 + RIM(잔여이익) 앵커를 산출한다.
철학: **공시 기반·근거 투명·예측 남발 X**. "적정가 X원" 블랙박스가 아니라 배수·인풋·가정을
모두 노출하고 사용자가 "밸류 위치"를 판단하게 한다(value_up tool과 결 동일).

## 1. 시계열 기준 3종

| 기준 | 뜻 | 적용 대상 | 데이터 |
|---|---|---|---|
| **FY0** | 최근 **사업연도**(연간 확정) | 모든 지표 | DART 사업보고서(11011) |
| **TTM** | 최근 **4개 분기 합** = 직전FY + 당기누적 − 전년동기누적 | **flow만** (순이익·매출·EBITDA·FCF·영업이익) | DART 분기보고서 |
| **MRQ** | 최근 **분기말 잔액**(합산 X, 최신 스냅샷) | **stock만** (자본·차입·현금) | DART 최근 분기 |

- **flow(합산)** vs **stock(잔액)** 구분이 시계열 기준을 가른다.
  - flow = 기간 누적 → TTM 성립. stock = 시점 잔고 → **TTM 불성립, MRQ(최신 잔액) 사용**.
  - 예: 자본은 stock. FY25(2025-12-31 잔액)와 1Q26(2026-03-31 잔액)은 그 사이
    `순이익 유보 − 배당 ± 기타포괄손익 ± 자본거래`만큼 다름. **최신인 1Q26 = MRQ**.
- **PBR "TTM"은 성립 안 함** → PBR은 FY0(연말자본) 또는 **MRQ(최근분기말 자본)**.
- **FWD(예측)** = 컨센 데이터 없음 → **제외**(원하면 "가정 입력형"으로 별도).

## 3. 측정 방식 — 공통 규칙 (맞는 아이템·맞는 방식)

- **가격·시가총액·상장주식수 = KRX Open API 공식** (`sto/stk_bydd_trd` MKTCAP·LIST_SHRS).
  우선주 존재 시: 시총/EV는 보통주 기준 + 우선주 별도 합산(경고 부착). PER·PBR·배당수익률은 정상.
- **순이익·EPS = 지배주주 귀속**(account_id `ProfitLossAttributableToOwnersOfParent`; nm substring 금지).
  TTM = FY + 당기누적 − 전년동기누적(4분기 합).
- **자본·BPS = 지배자본 ÷ 유통주식수**(자기주식 제외). 지배자본 = `EquityAttributableToOwnersOfParent`.
  FnGuide 규약 일치 검증됨(삼성전자 424조/6.63억주 = **BPS 63,997**).
- **순차입금 = 총차입(단기+장기) − 현금성자산** (MRQ 잔액).
- **EV = 시총 + 순차입금**.
- **EBITDA = 영업이익 + 감가상각비(D&A)** — D&A는 CF에서 추출. **추출 실패 회사는 N/A**(알려진 한계 →
  EV/EBITDA는 v1.1로, D&A 보강 후).
- **DPS = 현금배당총액 ÷ 유통주식수** (또는 배당 tool 현금DPS).
- **RIM 적정PBR = (ROE − g)/(CoE − g)**, 적정가 = 적정PBR × BPS(MRQ). CoE(요구수익률)·g(영구성장)는
  **투명 가정**(기본 CoE 9%, g 0%; 조정 가능). RIM은 보수적 앵커(고PBR·프랜차이즈 가치 미반영) — 단정 X.

## 4. 밴드(시계열) 측정 방식

"지금 밸류가 역사/동종 대비 어디"를 위한 자기 밴드:
- **각 시점 배수 = 그 시점 KRX 종가 ÷ 그 시점 DART 재무** → min·25%·중앙·75%·max + **현재 백분위**.
- **연간 밴드(v1)**: 최근 5개 **연말(결산일) 종가**(KRX 5콜=전종목) × 연도별 EPS/BPS → PER/PBR 5년 밴드.
- **분기 밴드(v1.1)**: 최근 20개 분기말 × TTM/MRQ 재무(KRX 20콜).
- **rolling 일별(v2)**: 일별 종가 × as-of TTM (가장 정밀, 용량↑).
- **peer 밴드(v1.1)**: 동종업종(WI26/KRX 섹터) 배수 중앙값 대비.

### 4.1 시점지정(as-of) 조회 — **PIT(Point-In-Time) = 공시 접수일 기준** (필수 원칙)

시점 D의 밸류를 낼 때 **가격 = KRX basDd(그 날 종가)**, **재무 = D 시점에 이미 공시돼 있던 최신 정기보고서**.

- **PIT 앵커 = 공시 접수일(rcept_dt), 결산기말(period-end) 아님.** FY2025 실적은 결산 2025-12-31이나
  공시는 **2026-3월 중순** → 2026-02 시점 최신 재무는 **FY2024**(2025-3월 공시). 결산기말로 매핑하면
  **look-ahead 편향**(미공시 미래 실적을 과거에 대입) = 백테스트 오류.
- **리졸버**: DART `list.json`(정기공시 pblntf_ty=A)로 종목의 사업·반기·분기 보고서 + **각 접수일** 조회 →
  `접수일 ≤ D` 중 최신 보고서 선택 → 그 보고서 재무로 그 시점 배수 계산.
- **정정공시**: PIT는 "그 시점 available했던 버전" → 원 공시(또는 D까지의 정정본) 사용, **재작성본 소급 금지**
  (accountant 지적 "as originally reported"와 동일 원칙).
- **배당(DPS)도 PIT**: 주총 결의(알림) 시점 이후에만 available.
- **최근 1주일 일단위**: 그 주엔 최신 보고서 동일 → 재무 고정, **가격만** 움직임(간단). 과거·월말은 매 시점 PIT 재무 매핑.
- 파라미터(제안): `as_of`(단일) / `dates`(리스트) / `period`("1w_daily"|"monthly"). 밴드도 이 PIT 규칙의 반복.

## 5. 데이터 소스·용량·rate limit

- **KRX Open API**(`data-dbg.krx.co.kr/svc/apis`, AUTH_KEY) — 하루 1콜에 전 종목 시세/시총/상장주식수.
  DART 분당한도(1,000)와 무관 → 서비스 IP 차단 리스크 없음. 정제 저장 시 전종목 10년 ~500MB, 코스피200 수십MB.
  ※ Open API엔 PER/PBR/배당수익률 **없음**(우리가 DART로 자체 계산). 투자자별·공매도·지수구성 미포함.
- **DART API** — 재무(사업/분기보고서), 배당. 종목당 다수 콜 → 배치 시 rate limit 준수(`hard-rate-limit` lesson).

## 9. 실시간 스케일 오류 가드 (260704, 소프트센 032680 사례로 확정) — 설계, 구현 대기

### 배경 — 두 메커니즘의 역할 분담

과거 연도(FY2020~2023) 스케일 오류는 **"다음 해 보고서의 전기(frmtrm/bfefrmtrm) 비교치"로 사후 정정**
가능함을 확인(소프트센 FY2022 순이익 10.7경원 → FY2023 보고서 전기란 10,723,795,687원으로 정정,
정확히 100만배 오류). `market_val_series.py backfill_restated()`로 2,508/2,599사(96.5%) 적용 완료.

**단, 이 방법은 구조적으로 "가장 최신 연도"엔 못 씀** — 다음 해 보고서가 아직 없기 때문. 그런데
`valuation.py`(개별 tool)·`market_val_agg.py`(시장 현재 aggregate)가 실제 노출하는 값은 항상
**"가장 최신 연도"**라, 정작 제일 중요한 데이터가 무방비였다. → **당일(같은 API 응답 안에서) 판정
가능한 실시간 가드**가 별도로 필요.

### 3인 전문가(financial analyst · data QA engineer · quant PM) 검토 종합 (260704)

**핵심 발견(QA)**: DART `fnlttSinglAcntAll` 응답 하나에 이미 **thstrm(당기)·frmtrm(전기)·

### 소비 맥락별 처리 분기 — "값 무효화 vs 값 유지+경고" (260704 확정)

"오류 의심값을 아예 지워(N/M) 마스킹하는 게 맞나"는 근본 질문 → **소비 맥락에 따라 답이 갈린다**로 결론:

| 소비처 | 처리 | 이유 |
|---|---|---|
| **개별 종목 조회**(`valuation.py`) | **값 유지 + 강한 경고**(🚨), 무효화 안 함 | 사람이 화면에서 숫자를 직접 봄 → 경고를 읽고 스스로 판단 가능. 이 tool의 철학("배수·인풋·가정 모두 노출, 판단은 사용자")·자본잠식 처리(값 유지+경고)와 일관. ②③도 100% 확신 아니므로 드문 오탐 시 원본조차 못 보게 만드는 N/M은 과함. `data_quality.scale_tier`·`values_masked=False`로 기계 소비자에게도 판정 노출. |
| **시장 aggregate**(`market_val_agg`·`market_val_series`) | **무효화(제외)** | 기계가 ΣNI/Σ시총으로 그냥 합산 → 경고문이 합산 연산에 무력. 오염값 1건이 시장 전체 PER을 망가뜨림(소프트센이 KOSDAQ 2023 PER을 N/M으로 오판시킨 실제 사고). 단 `[가드]` 로그로 원본·제외사유 보존(화면에서 사라지는 것 ≠ 기록에서 사라지는 것). |

즉 **"방어력 vs 투명성" 트레이드오프를 이분법이 아니라 소비 맥락으로 해소** — 사람이 보는 곳은
투명성 우선(값+경고), 기계가 더하는 곳은 방어 우선(무효화+로그). valuation.py 15개사(대·중·소형
혼합) 재검증 오탐 0.

### ② 항등식 스모크 테스트 (260704, 20개사 무작위) — **정확일치 필수, substring 금지**

무작위 20개사 FY2024 CFS/OFS로 실측: **자산총계 = 부채총계 + 자본총계, 20/20 오차 0.0000%**(허용오차
불필요, 회계 항등식이므로 당연). 단 1차 시도에서 `account_id` 매칭을 substring(`in`)으로 했다가
1건(005110) 96.7% "불일치"로 오탐 — 원인은 `"ifrs-full_Liabilities" in "ifrs-full_LiabilitiesIncludedIn
DisposalGroupsClassifiedAsHeldForSale"` 가 True가 되는 접두어 충돌(매각예정처분부채집단을 부채총계로
오인)이었음. `financial-metrics-account-id-260630`과 동일 클래스의 실수 재발.
**교훈**: ②번 구현 시 `account_id`는 반드시 **정확일치(`==`)**로 비교 — substring 매칭 절대 금지
(CLAUDE.md "순서/위치 기반 접근 금지" 원칙과 같은 결의 이름 기반 정확 매칭 원칙). 정확일치로 재실행 시
20/20 완전 일치 확인 → **②번 그대로 채택**(불안정하면 드랍 검토 예정이었으나 불안정성의 원인이
항등식이 아니라 구현 버그였음이 확인돼 유지).

### 코드 구현 + 실사고(소프트센) 재검증 — **①②번이 이 정확한 사고엔 무력함을 발견** (260704)

`open_proxy_mcp/services/scale_guard.py` 구현 후 **소프트센 FY2022 실제 사고로 역검증**했더니
예상 밖 결과가 나왔다:

```
FY2022 보고서 자체의 당기(thstrm) = 10,723,795,687,000,000
FY2022 보고서 자체의 전기(frmtrm) = 15,030,454,636,000,000   ← 이것도 똑같이 100만배 부풀려짐!
→ 당기/전기 비율 = 0.71배 (정상 범위처럼 보임) → ①번(배수점프) 미탐지
→ 자산=부채+자본도 내부적으로 여전히 성립(둘 다 같이 부풀려져서) → ②번(항등식) 미탐지
→ 자릿수(17자리>16) 탐지 ✅ / 시총비율(69만배>50배) 탐지 ✅
```

**원인**: 이 필터의 XBRL 단위오류는 **보고서 전체(당기·전기 컬럼, 재무제표 전 항목)를 동일 배율로
일괄 부풀린 것** — "한 항목만 실수로 배율이 안 맞은 것"이 아니라 "보고서 작성 소프트웨어/스프레드시트
단계에서 전체를 잘못된 단위로 일괄 입력"한 것으로 추정됨. 그 결과 **같은 보고서 내부 비교(①②)는
서로 다 똑같이 틀려서 오히려 "일관돼 보이는"** 역설적 상황이 발생.

**수정된 우선순위 (실측 근거)**: ③(자릿수)·④(시총비율) — **외부 기준(물리적 상한·시가총액)과 대조하는
체크만 이 사고를 잡았다.** ①②(같은 보고서 내부 정합성 체크)는 "내부적으로 일관된 오류"엔 원천적으로
무력함이 이번 실사고 재검증으로 확인됨. 단, ①②는 **"보고서 일부 항목만 실수로 틀린" 다른 유형의
오류**(예: 순이익만 오타, 자산총계만 오기)에는 여전히 유효할 수 있어 드랍하지 않고 유지 — 4개 체크를
모두 유지하되, **③④를 최종 방어선으로 재확인**하는 방향으로 이해를 갱신.

**20개사(무작위) 종합 재검증**: `assess()` 4체크 통합 판정 결과 **20/20 전부 `clean`**(오탐 0건) —
정상 종목엔 어떤 체크도 안 걸림을 재확인. account_id 추출(NI·자본)도 기존 프로덕션 코드(substring
방식)와 exact-match 방식을 20개사 교차검증 → **0/20 불일치**(현재는 우연히 충돌 없었으나, 원리상
여전히 취약하므로 exact match로 통일 교체 예정).

### ③ 재설계 — 고정 자릿수 → "시장 내 실측 최댓값 대비 배수" (260704)

배선 후 실제 사고 재검증에서 ①②가 무력함을 확인한 뒤, "그럼 결국 뭘 쓰면 되냐"는 질문에 답하며
③(자릿수 16 고정값)의 설계 자체를 재검토 — **고정 절대값 임계치는 회사 규모를 안 가려 원리적으로
이상하다**는 지적에 따라 시나리오 검증:

```
소형주(시총150억) 순이익 100억이 배율오류를 겪는 경우:
  10배   → ③✗ ④✗       100배  → ③✗ ④✓(67배)     1,000배 → ③✗ ④✓(667배)
  1만배  → ③✗ ④✓(6667배) 100만배(소프트센급) → ③✓ ④✓

대형주(시총1800조) 순이익 44조가 같은 배율오류를 겪는 경우:
  10배 → ③✗ ④✗(0.2배)   100배 → ③✗ ④✗(2.4배)  ← 아무 체크도 못 잡는 사각지대!
  1,000배 → ③✓(17자리) ④✗(24배, 50배 미달)
```

**발견**: ③(고정 자릿수)은 소형주의 중간배율(100~1만배) 오류를 전부 놓치고, ④(시총비율)는 대형주에서
분모(시총)가 커서 오히려 둔감해짐(100배 오류도 24배 수준 비율이라 50배 임계치 미달) — 두 체크가
**회사 규모 축을 따라 서로 다른 사각지대**를 가짐, 특히 "대형주 100배 오류"는 기존 ③④ 둘 다 놓침.

**해결**: ③을 "시장 내 실측 최댓값(현재 삼성전자 순이익 44.26조) 대비 3배 초과"로 재정의
(`check_market_relative_cap`). 재검증 결과 10배부터 100만배까지 전 배율·소형/대형 안 가리고 잡히고,
2등(SK하이닉스 42.9조)은 오탐 없음(3배 여유 충분). 기존 자릿수 체크는 `market_max` 미제공 시(단독
실행 등)의 최후 백스톱으로만 유지.

**앵커 오염 위험 발견·차단**: 앵커를 "DB의 살아있는 MAX()"로 동적 확장하면, 이미 오염된 값(소프트센
FY2022 원본 1.07×10^16이 구버전 배치로 `mkt_fund_hist`에 그대로 남아있음)이 그대로 앵커가 되어
**가드 자체가 무력화되는 자기오염**을 실측으로 확인 → 검증된 상수 앵커(`MARKET_MAX_NI_ANCHOR`,
scale_guard.py 단일 지점)만 사용, DB MAX와 블렌딩하는 곳(market_val_agg.py)은 `scale_flag IS NULL`
필터로 이미 걸러진 데이터인지 확인 후 허용.

**최종 결론(반복 질문에 대한 답)**: "4개 중 뭘 쓰나"는 오답 — 체크마다 잡는 오류 유형·회사규모
사각지대가 다르므로 **OR 로직(하나라도 걸리면 hard)이 정답**이고, "2개 이상 동의 요구"는 서로 다른
체크가 서로 다른 경우를 잡는다는 사실 자체를 무력화시켜 **오히려 실제 오류를 놓치게 됨**(2-of-4 요구
시 소프트센류 특정 배율대 사고를 원천 누락). 단 여전히 남는 잔여 사각지대(예: 매우 낮은 배율의
대형주 오류, 100배 미만)는 이론상 존재하며 문서화만 하고 v1.1로 이월.

### ①번 hard 제외 — "진짜 데이터를 가짜로 마스킹" 우려의 실측 확인 (260704)

사용자가 "이 가드가 진짜 데이터를 가짜로 마스킹할까봐 걱정"이라고 지적 → `mkt_fund_hist` 전수
(12,995행, YoY 연속쌍 기준)로 ①(당기/전기 배수점프)의 실제 오탐률 측정:

```
①번 hard 트리거 40건 중 — 진짜 스케일오류(소프트센) 1건, 정상 실적급변동(오탐) 39건 (오탐률 97.5%)
```

**원인**: "비율이 10의 거듭제곱에 ±20% 근접"이라는 기준은 통계적으로 생각보다 관대해서, 중소형사의
**정상적인 적자↔흑자 전환·일회성 손익**이 우연히 그 근처에 걸리는 경우가 매우 흔함(예: 000480社
409억→4억, 003120社 -15억→1,380억 — 전부 진짜 실적, 오류 아님). 초기 표본검증(대형 우량주 위주
40여개사)에선 안 드러난 사각지대 — **표본이 중소형·고변동성 종목을 충분히 포함하지 못했던 것**.

**조치**: ①을 hard 등급에서 제외, **soft(정보성 경고만, 값은 유지)로 격하**. 재검증 결과 hard
트리거 **1건(소프트센, market_relative_cap만으로 정확히 포착)**, 오탐 0건. **최종 hard 등급 = ②
(항등식)·③(시장최댓값 배수) 둘만.** ①④는 soft(정보성)로 유지 — 값을 지우지 않고 참고 경고만 붙임,
"불확실하면 지우지 말고 표시"라는 QA 원칙과 일치하도록 재정렬.

**교훈**: 표본검증(40여개사)은 "오탐이 없다"를 증명하는 데는 유용했지만, **표본이 대형 우량주
위주였다는 편향** 때문에 정작 위험이 집중된 중소형·고변동성 종목 구간의 결함을 놓쳤다. 전수(실제
수집된 12,995행) 재검증이 아니었다면 이 오탐 97.5%는 프로덕션에 그대로 나갔을 것 — 표본검증과
전수검증을 모두 하라는 프로젝트 원칙(작업 수행 원칙 2)이 실제로 값어치를 증명한 사례.
